# Git Rebase 与 Merge 的区别

在 Git 中整合不同分支的修改主要有两种方式:`merge` 和 `rebase`。理解它们的差异对维护清晰的提交历史非常重要。

## merge 的工作方式

`git merge` 会保留两个分支的所有提交历史。它会在合并点创建一个新的 "merge commit",这个 commit 有两个父提交,体现了"两条线汇合"的含义。合并之后的历史是真实的——你能看到分支在哪里分叉、谁在什么时候合入了什么。

合并后的历史可能看起来比较乱。如果多人频繁合并 feature 分支,主干上会出现很多分叉和汇合的节点。对于追溯"某行代码是谁引入的"很有帮助,因为历史没有被改写。

## rebase 的工作方式

`git rebase` 的核心思想是"重放提交"。它会把你当前分支上的所有提交"摘下来",然后在目标分支的最新提交之上依次重新应用。应用完之后,你的提交看起来就像是在目标分支最新状态之后写的——历史变成了一条直线。

因为提交被重写了(commit hash 会变),rebase 会改写历史。所以官方推荐:**永远不要对已经推送到公共仓库的提交做 rebase**。否则其他协作者的本地历史会和远程不一致,会非常痛苦。

## 实际选择

简单经验法则:
- 自己的本地 feature 分支还没推:用 rebase,保持历史干净。
- 多人协作的分支,或者已经推送的分支:用 merge,保留真实历史。
- 团队最好约定一种风格,避免每个人的历史长得都不一样。

merge 和 rebase 也可以组合使用:先 rebase 自己的本地分支到最新的 main,再 merge 进 main。这是相当常见的工业级工作流。
